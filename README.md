# VLSE — سامانهٔ ارزیابی و رتبه‌بندی کیفی تأمین‌کنندگان

سامانهٔ ثبت، ارزیابی و انتخاب تأمین‌کنندگان مواد اولیهٔ دارویی (API) مطابق الزامات GxP/GMP. رابط کاربری کاملاً فارسی و راست‌به‌چپ است و همهٔ تغییرها در یک audit trail کامل با مقدار قبل و بعد ثبت می‌شوند.

| لایه | فناوری |
| :--- | :--- |
| فرانت‌اند | React 19 · Vite 6 · TypeScript · Tailwind CSS 4 · فونت Vazirmatn |
| بک‌اند | Express 5 (`server.ts`) |
| دسترسی به داده | Prisma 5 |
| پایگاه‌داده | PostgreSQL — **تنها منبع حقیقت** |

---

## سامانه چه کاری می‌کند

- **مخزن مواد اولیه:** نام فارسی و لاتین، CAS، نقش ماده، فارماکوپه، محصول نهایی و فایل Specification.
- **مخزن شرکای تجاری:** تولیدکننده و فروشنده به‌شکل مستقل؛ فروشنده با مدارک ۵گانهٔ SOP ارزیابی و گریدبندی می‌شود و **فقط فروشندهٔ گرید A** می‌تواند به یک سورس وصل شود (سرور این قاعده را اعمال می‌کند، نه فقط فرم).
- **سورس‌ها:** هر ترکیب «ماده + تأمین‌کننده» یک سورس است، در شش دستهٔ خرید خارجی، خرید داخلی، دامی، اقلام بسته‌بندی، نمونه و لیست سیاه.
- **ارزیابی چنددپارتمانی:** بازرگانی، کیفیت، برنامه‌ریزی و مالی هرکدام فقط بخش خودشان را امتیاز می‌دهند و امتیاز کل به‌صورت میانگین وزنی محاسبه می‌شود.
- **ارزیابی ریسک (FMEA)** و **ثبت نتایج آزمایشگاهی (QC)** که هر دو در امتیاز نهایی موتور پیشنهاددهنده اثر می‌گذارند.
- **انتخاب سورس:** موتور فقط **پیشنهاد** می‌دهد؛ تصمیم نهایی را کارشناس با ثبت دلیل اجباری می‌گیرد.
- **ردیابی تغییرات:** هر نوشتن با کاربر، زمان، دلیل و مقایسهٔ قبل/بعد ثبت می‌شود.
- **خروجی اکسل و فرم‌های چاپی A4** برای مستندسازی و ممیزی.

## نصب

### پیش‌نیازها

- **Node.js 20** (تصاویر Docker پروژه روی `node:20-alpine` هستند)
- **PostgreSQL 13 یا بالاتر** (پیشنهاد: ۱۵) با مجوز ساخت جدول و ایندکس
- **Bun** برای توسعهٔ محلی، یا npm

### نصب برای توسعه

```bash
git clone https://github.com/mj67git/Vendorlist-to-claude.git
cd Vendorlist-to-claude
bun install            # پروژه با bun.lock نصب می‌شود
cp .env.example .env   # سپس مقادیر واقعی را در .env بگذارید
```

حداقل متغیرهای لازم در `.env`:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE?schema=public
JWT_SECRET=<خروجی: openssl rand -base64 48>
```

> `JWT_SECRET` باید حداقل ۳۲ کاراکتر باشد. در حالت production اگر تعریف نشده باشد، سرور عمداً بالا نمی‌آید.

ساخت جدول‌ها و دادهٔ اولیه:

```bash
bunx prisma migrate deploy   # اعمال مهاجرت‌ها
bunx tsx prisma/seed.ts      # ساخت کاربران پیش‌فرض
```

### نصب روی سرور (Docker)

بستهٔ آمادهٔ استقرار در مخزن جداگانهٔ `vlse-release` است و نصبش یک دستور دارد:

```bash
./deploy/install.sh
```

اسکریپت پیش‌نیازها را می‌سنجد، `.env` را با رمز پایگاه‌داده و کلید نشستِ تصادفی می‌سازد، تصویر را build و سرویس‌ها را بالا می‌آورد، تا سالم شدن سامانه صبر می‌کند و آدرس ورود را چاپ می‌کند. همین دستور مسیر به‌روزرسانی هم هست و داده را دست نمی‌زند. جزئیات کامل در `IT_DEPLOYMENT_GUIDE.md`.

## اجرا

```bash
bun run dev      # سرور توسعه روی http://localhost:3000
```

`server.ts` هم API را سرو می‌کند و هم فرانت را از طریق Vite dev middleware، پس نیازی به اجرای جداگانهٔ Vite نیست.

| دستور | کار |
| :--- | :--- |
| `bun run dev` | اجرای محیط توسعه |
| `bun run build` | مهاجرت + build فرانت + باندل سرور در `dist/` |
| `bun run start` | اجرای نسخهٔ ساخته‌شده (`dist/server.cjs`) |
| `bun run lint` | بررسی نوع با `tsc --noEmit` |
| `bun run lint:eslint` | ESLint |
| `bun run test` | کل تست‌ها (ترتیبی) |
| `bun run check` | هر چهار مورد بالا، پشت سر هم |

**دربارهٔ تست‌ها:** تست‌های API برنامهٔ واقعی را روی یک PostgreSQL واقعی بالا می‌آورند. اگر `DATABASE_URL` تعریف نشده باشد، خودشان skip می‌شوند و تست‌های واحد اجرا می‌شوند. برای اجرای کامل:

```bash
export DATABASE_URL="postgresql://postgres@localhost:5432/vlse_test?schema=public"
export JWT_SECRET="یک-کلید-حداقل-۳۲-کاراکتری-برای-تست"
bunx prisma migrate deploy
bun run test
```

**ورود اولیه:** با `prisma/seed.ts` نام کاربری `admin` و رمز `123`. روی استقرار تازه (بدون seed) کاربران پیش‌فرض در اولین اجرا ساخته می‌شوند و رمز اولیه `123456` است که سامانه در همان ورود اول تغییرش را اجباری می‌کند.

## مثال استفاده

### الف) از راه رابط کاربری — ثبت یک سورس تا انتخاب نهایی

1. **مادهٔ اولیه را ثبت کنید:** «مخزن مواد اولیه» ← «ثبت مادهٔ جدید» (نام فارسی و لاتین، CAS، نقش ماده، فارماکوپه، محصول نهایی).
2. **تأمین‌کننده را ثبت کنید:** «مخزن شرکای تجاری» ← تولیدکننده یا فروشنده. برای فروشنده، مدارک ۵گانهٔ SOP را ارزیابی کنید تا گرید بگیرد.
3. **سورس بسازید:** در دستهٔ مربوطه (مثلاً «خرید خارجی») ← «ثبت سورس جدید»، ماده و تأمین‌کننده را انتخاب کنید. اگر فروشنده گرید A نداشته باشد، سرور اتصال را رد می‌کند.
4. **امتیاز بدهید:** در صفحهٔ سورس، هر دپارتمان بخش خودش را پر می‌کند. گرید و وضعیت خودکار از امتیاز مشتق می‌شوند.
5. **ریسک و نتایج آزمایشگاه را ثبت کنید:** فرم FMEA و رکوردهای QC.
6. **سورس را انتخاب کنید:** در صفحهٔ دسته، پنل «مقایسه و انتخاب سورس این ماده» رتبه‌بندی موتور را نشان می‌دهد. دکمهٔ «ثبت انتخاب سورس» تصمیم را با **دلیل اجباری** ثبت می‌کند.

### ب) از راه API

```bash
# ۱. ورود و گرفتن توکن
TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"username":"admin","password":"123"}' | jq -r .token)

# ۲. فهرست سورس‌ها
curl -s http://localhost:3000/api/vendors -H "authorization: Bearer $TOKEN" | jq '.[0].name'

# ۳. ثبت امتیاز یک دپارتمان
#    expectedUpdatedAt همان مهر زمانی است که موقع خواندن رکورد گرفته‌اید؛
#    اگر رکورد در این فاصله تغییر کرده باشد، سرور با ۴۰۹ رد می‌کند.
curl -s -X PATCH http://localhost:3000/api/vendors/V1/scores \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{
        "scores": {"commercial": 88, "qa": 92, "planning": 85, "finance": 90},
        "reasonForChange": "ثبت ارزیابی دوره‌ای ۱۴۰۵",
        "expectedUpdatedAt": "2026-09-03T10:00:00.000Z"
      }'

# ۴. آنچه از آخرین بازدید تغییر کرده (همگام‌سازی سبک)
curl -s "http://localhost:3000/api/vendors/changes?since=2026-09-03T10:00:00.000Z" \
  -H "authorization: Bearer $TOKEN"
```

سه قاعده که هنگام کار با API باید بدانید:

- **دسترسی سمت سرور اعمال می‌شود.** گیت‌های نقش در فرانت فقط برای تجربهٔ کاربری‌اند؛ هر endpoint حساس خودش مجوز را بررسی می‌کند. پاسخ ۴۰۱ یعنی توکن نامعتبر و ۴۰۳ یعنی نداشتن مجوز.
- **PATCHهای یک سورس باید ترتیبی فرستاده شوند.** هر endpoint کل رکورد را می‌خواند و می‌نویسد؛ دو درخواست هم‌زمان روی یک سورس باعث گم‌شدن یکی می‌شود. سرور هم قفل per-record دارد.
- **`reasonForChange` را بفرستید.** دلیل تغییر بخشی از سابقهٔ ممیزی است.

## چند تصمیم معماری که خوب است بدانید

- **PostgreSQL تنها منبع حقیقت است.** هیچ fallback فایلی وجود ندارد؛ `localStorage` فقط کش نمایش آفلاین است. اگر پایگاه‌داده در دسترس نباشد، سرویس بالا می‌آید ولی مسیرهای داده خطا می‌دهند — `/api/health` این را با کد ۵۰۳ گزارش می‌کند.
- **گرید و وضعیت «مردود» محاسبه‌شونده‌اند، نه ذخیره‌شونده.** تصمیم از `src/utils/vendorState.ts` می‌آید و همه‌جا باید از همان خوانده شود.
- **جدول سیاست دسترسی یکی است** (`src/utils/permissions.ts`) و هم سرور و هم رابط کاربری از همان می‌خوانند.
- **کار هم‌زمان چند کاربر** سه لایه دارد: قفل per-record، گارد نسخه با پاسخ ۴۰۹، و همگام‌سازی پس‌زمینه که فرم در حال ویرایش را هرگز بازنویسی نمی‌کند.

قواعد کامل و دلیل هرکدام در `CLAUDE.md` آمده است.
